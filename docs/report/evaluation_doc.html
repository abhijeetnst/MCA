The project in plain language

What we built, why it matters, and how it works — explained with everyday analogies, no hardware jargon.

What problem are we solving?

Computers constantly need to multiply matrices — big grids of numbers multiplied together. This one calculation sits underneath almost everything modern: neural networks and AI (like ChatGPT), image and face recognition, recommendation systems, graphics, and signal processing. Inside those systems, matrix multiplication is easily 80–90% of all the maths being done.

A normal computer processor does maths one small piece at a time, like one worker solving a huge worksheet row by row. For small matrices that is fine. For the enormous matrices used in AI, it becomes the single biggest bottleneck — the maths is simple, but there is just so much of it.

What did we make?

We designed a special-purpose circuit — think of it as a tiny calculator dedicated to exactly one job — and wrote it in Verilog, a language for describing circuits. And to be completely clear: everything in this project is software. We never built a physical chip and never touched any hardware board. The design was run as a simulation on a computer, which behaves exactly like the real circuit would, and it was checked with the same professional software tools that chip engineers use to plan a chip before it is ever manufactured.

This circuit does one job only: matrix multiplication. But it does that one job many times in parallel, like replacing a single worker with an entire workshop of workers, each doing their own small piece at the same moment.

Our workshop is a 4×4 grid of 16 tiny calculators. Each one can only multiply two small numbers and keep a running total. That sounds too simple to be useful — the magic is in how the numbers flow through the grid.

The assembly-line idea (this is the heart of the project)

Imagine an assembly line in a factory. Raw parts enter from the left edge and from the top edge of the grid, one batch per tick of a clock, like a conveyor belt moving one step every beat.

  • The numbers of matrix A march along the rows, left to right.
  • The numbers of matrix B march down the columns, top to bottom.
  • Each little calculator sits at a grid point. Every clock tick, it takes whatever A-number and B-number just arrived at its door, multiplies them, adds the result to its running total, and passes both numbers on to its neighbours.

Because of the careful timing of the belts, the right pairs of numbers always meet at the right calculator at the right moment. Calculator at position (row 2, column 3) is exactly where A's row 2 numbers and B's column 3 numbers pass each other — so its running total ends up being precisely the dot product the answer matrix needs at position (2,3).

When the last pair has passed through, every calculator holds one finished entry of the answer matrix C, and the result can be read out. The name for this style of hardware is a systolic array — "systolic" comes from systole, the pumping of a heart: data pulses through the grid the way blood pulses through the body.

Why is this clever?

Every one of the 16 calculators is busy on every single clock tick. No waiting, no idling. A normal design would do one multiplication per tick; ours does up to 16 at once. And each calculator only talks to its immediate neighbours, so the wiring is short — which is exactly why this is the architecture Google chose for the TPU chip that runs AI in their data centres.

How much faster is it, really?

To prove the speed-up is real and not just on paper, we also built a "normal" comparison version — a design that multiplies matrices the slow, one-at-a-time way, with exactly the same inputs and outputs. Then we raced them:

And the gap keeps growing: the normal design's work grows as N×N×N (cube), while ours grows as just 3×N (three times the width). Double the matrix size and the normal design does 8× the work; ours just takes a couple more clock ticks.

How do we know it actually works?

We did not just design it and hope. We wrote automated tests that compare the design's answer, number by number, against the same multiplication done in ordinary software:

  • The tiny calculator itself was tested with all 65,536 possible multiplications of two 8-bit numbers — every single one correct.
  • The full system ran 26 carefully chosen test matrices — easy ones (all zeros, identity), extreme ones (all largest positive, all most-negative values), and random ones — and for every single case our design matched the software answer exactly.
  • We deliberately broke the design in small ways to check that our tests would actually catch a bug (they did — nearly every test failed when the timing was shifted by one tick). This proves the tests are sharp, not just rubber stamps.
  • Finally, we ran the design through chip-planning software — the same open-source tools (Yosys, nextpnr) engineers use to check a design before a chip is ever built. Those tools reported how much chip area the design needs and how fast a clock it could handle: it fits comfortably, with a projected top speed of 52.3 MHz.

Where is this used in the real world?

  • Google's TPU — the chip that powers Google's AI services — is at its heart a large systolic array, exactly the concept we built (theirs is 256×256, ours is 4×4).
  • AI chips in phones and data centres (Apple, NVIDIA, Qualcomm) all use some form of this array-of-multipliers idea for neural network maths.
  • Video and image processing — filters and transforms are matrix multiplications.
  • Signal processing — radar, wireless (5G), and audio processing all lean on matrix operations.

In short: we designed a miniature, working model of the engine that powers modern AI hardware — wrote it ourselves, verified it exhaustively in simulation, measured its speed-up honestly, and confirmed with professional tools that it could be manufactured as a real chip. And the whole thing is software: every result in this project comes out of a simulation or a tool report, reproducible by anyone with the four make commands in our repository.

The project the technical way

A parameterised N×N output-stationary systolic array in synthesizable Verilog: INT8 inputs, 32-bit accumulation, 3N compute cycles vs N³ for a single-MAC baseline. All results are from simulation and open-source EDA tools (Verilator, Yosys, nextpnr) — no hardware was built.

Specification and top-level architecture

The system computes C = A × B for N×N signed 8-bit matrices (default N = 4) with 32-bit accumulators — wide enough that overflow is impossible for INT8 inputs up to N ≈ 131k. Both the accelerator (systolic_top) and the baseline (seq_matmul) expose an identical memory-mapped data interface:

write: we=1, sel=0(A)|1(B), addr=row*N+col, din=INT8
run: pulse start → wait done
read: rd_addr=row*N+col → rd_data = C[row][col] (INT32)

The top level holds A and B in register-array buffers and performs the skew by indexing rather than with shift registers: at systolic step t, row i is fed A[i][t−i] from the left and column j is fed B[t−j][j] from the top (zero when the index is out of range). This eliminates an entire class of skew FIFO logic.

Processing element

Each PE contains a combinational MAC — a signed 8×8→16-bit multiply followed by a 32-bit add — plus three registers: a_out, b_out (the pass-through pipeline registers) and acc (the local accumulator). Control inputs clr (zero all registers) and en (advance one step) come from the central FSM. The array is an N×N generate grid; A flows right, B flows down, and C[i][j] remains stationary in PE(i,j) — hence output-stationary.

Controller FSM and cycle math

IDLEwait for start
→
CLEARclr=1: zero all acc + pipeline regs
→
FEEDen=1, t = 0 … 3N−3: one MAC per PE per cycle
→
DONEdone=1: results readable via rd_addr

Why 3N−2 feed cycles: the skew makes A[i][k] and B[k][j] meet in PE(i,j) exactly at step t = i + j + k. The last product (i = j = k = N−1) arrives at t = 3N−3. Adding the IDLE→CLEAR and CLEAR transitions gives 3N cycles from start to done, against 1 + N³ for the sequential baseline. A wavefront of active PEs sweeps the anti-diagonal of the array; peak utilisation of all N² MACs/cycle is reached in the middle of the run, giving an average of N²·(3N−2)/3N ≈ N² − N²/3N MACs/cycle.

Verification methodology

  • PE level: exhaustive MAC check over all 65,536 INT8×INT8 pairs (0 mismatches), 16 directed PE tests, 200 random accumulate steps — ALL TESTS PASSED, enforced by non-zero exit codes.
  • System level: 26 directed + random cases run on both designs against a triple-loop reference model — counting, identity, zero, all-+127, all-−128 (the two's-complement extreme), mixed-sign extremes, and 20 random cases. Cycle counts are asserted alongside the data.
  • Parameter sweep: all 26 cases re-run for N = 2, 3, 4, 8.
  • Cross-check: scripts/plots.py independently re-reads A and B from the VCD waveform, computes A@B in numpy, and asserts equality with the accumulators.
  • Mutation testing: a one-step skew error fails 25/26 cases; terminating FEED one cycle early fails 26/26 — the testbench provably catches realistic bugs.
  • Lint: Verilator -Wall clean, with one justified local lint_off for the intentionally unused edge outputs.

  • nextpnr-ice40 (HX8K, no DSP blocks) builds all 16 multipliers from LUTs — hence 2.5× the logic cells of the baseline.

Known limits and design decisions (honest engineering)

  • Input buffers are register arrays — fine for small N; move to BRAM for N ≥ 16.
  • One matmul at a time; the next load is not overlapped with FEED. Back-to-back pipelined runs would approach the N² peak.
  • Writes during a run are not blocked and start is ignored while busy — the host must wait for done.
  • N ≥ 2 (N = 1 degenerates the address width); addresses ≥ N² are unguarded for non-power-of-two N.
  • Accumulators have no reset — only clr at start, so they read X in simulation before the first run (0 on FPGA power-up).
